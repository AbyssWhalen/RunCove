# RunCove v0.3.0 Run Log Archive Plan

## Summary

- Build from the released `v0.2.1` baseline. v0.3.0 ships one feature: an
  opt-in, quota-bounded, on-disk archive of run-session output, plus the history
  and viewer surfaces needed to read it.
- Close the gap the repository already records: session output lives only in a
  bounded in-memory buffer, is not written to disk, and is not correlated to
  run-session IDs (`HANDOFF.md:126-128`, `notes.md:227`). Run history can list a
  session but never show what it printed.
- The feature is off by default. Enabling it applies only to sessions started
  afterwards.
- One SQLite migration from schema version 1 to version 2 adds one index table.
- Keep the Windows-first desktop application, the existing Overview, Ports, and
  Projects navigation, the process-safety model, the port trust order, and the
  compatibility CLI unchanged. During implementation, do not change CI,
  release workflows, tags, published releases, or repository settings, and do
  not commit, push, or publish before separate authorization.

## Scope Decision

Run log archiving and project Git status were planned as two independent
milestones in one version. They are now separate versions.

- The archive alone contains a schema migration, a background write queue, file
  quota accounting with eviction, a crash-recovery sweep, and a new viewer. That
  is a full release of risk. Adding an unrelated feature to the same version
  means one milestone's failure can hide the other's, and a rollback cannot be
  targeted. Note what a release rollback does not cover: unpublishing v0.3.0 does
  not return an already-migrated database to version 1, so a user who launched
  v0.3.0 once cannot go back to v0.2.1 with that file. One more reason to keep the
  version's surface small.
- Git status also adds a large new dependency tree, and therefore a new audit
  surface, build-time cost, and minimum-toolchain question, to a release whose
  own evidence should be about persistence and quota behavior.
- The archive closes a limitation this repository already documents
  (`notes.md:227`). Git status closes none, and duplicates what the user's
  editor and Git client already show. It should be justified on its own merits,
  in its own version, or dropped.

## Implementation

### Record Format And Encoding

- Store one append-only file per run session in a dedicated subdirectory of the
  application-local data directory, `<app-data>/run-log-archives/`, and keep only
  an index row in SQLite. `<app-data>` is the directory `lib.rs:234-236` already
  creates and opens `runcove.sqlite3` in; the archives go in a child of it, not
  beside the database. Session output is unbounded single-session text that can
  reach several MiB; keeping bodies out of the database avoids database growth,
  avoids delete plus `VACUUM` on every eviction, and leaves existing queries
  untouched.
- Write JSON Lines, one record per physical line:
  `{"t":<epoch-ms>,"s":"stdout|stderr|system","l":"<text>"}`. Child output can
  contain tabs and carriage returns, so escape it rather than inventing a
  delimiter. One record per line keeps paging cheap and makes a truncated final
  record detectable and discardable after a crash.
- The archive stores the text the live drawer received, not the child's raw
  bytes. `capture_stream` already decodes with `String::from_utf8_lossy`
  (`processes.rs:815`) before any consumer sees a line, so invalid UTF-8 is
  replaced with `U+FFFD` upstream of the archive. The archive is fed the
  finished `RunLogEvent`, so an archived line is identical to the line the
  drawer showed, including the 16 KiB bound and truncation marker
  (`processes.rs:17-18`).
- Do not add a base64 or raw-byte field. It would give every line a second,
  unreadable copy of itself, create two sources of truth for one line, and serve
  only an export path that is out of scope. Byte-exact capture is a change to
  the live decode path, not to the archive format.
- The first draft's acceptance criterion "JSON Lines round-trips invalid UTF-8"
  is therefore deleted as unachievable and replaced by: for the same child
  output, the archived line equals the emitted `RunLogEvent.line` exactly.
- Recorded, out of scope: because the live path is UTF-8 only, a child that
  writes Windows console codepage bytes such as CP936 is already displayed as
  replacement characters before archiving, and the archive reproduces that
  faithfully. This is an existing limitation of the log feature, not one this
  milestone introduces. It is worth a separate decision and a cheap experiment;
  do not change the decode path inside this milestone.

### Archive Directory And Path Constraints

The sweep deletes files it does not recognize, and the viewer opens a path built
from a database column. Both are only safe if the directory is RunCove's alone and
the name is validated before it is joined to anything.

- One dedicated directory, `<app-data>/run-log-archives/`, created by the archive
  initialization and owned entirely by RunCove. It must never be the data
  directory itself, which also holds `runcove.sqlite3`, whatever journal file
  SQLite creates beside it, and whatever a future version adds. "Delete what has no
  index row" is a rule in a directory RunCove owns and a hazard in one it shares.
  (Measured 2026-08-16 and again 2026-08-17: neither developer data directory holds
  a `-wal` or `-shm` file, because `Storage::open` never sets `journal_mode` and the
  default rollback journal is transient. An earlier draft of this bullet named those
  two files as if they were always present; the argument does not depend on them.)
- File name generation rule, the only rule that produces a name:
  `<session-id>.jsonl`, exactly one path component. `<session-id>` is the session
  identifier from `run_sessions.id`, which `new_id` (`storage.rs:741-742`)
  produces as a lowercase hyphenated UUID v4, so a generated name matches
  `^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}\.jsonl$` and
  nothing else does. The same predicate answers both questions the code asks —
  "may I use this `file_name`?" and "did this build generate this directory
  entry?" — so the two can never disagree.
- `file_name` is validated against that rule every time it is read from the
  database, before it is joined to the archive directory. Rejected outright, with
  an explicit error and without touching the filesystem: an absolute path
  (`C:\...`, `\\?\...`, a UNC path, a leading `/` or `\`), a drive-relative path
  (`C:name.jsonl`), any `.` or `..` component, any name containing `/` or `\`, an
  empty name, a name whose stem is not a UUID, and any extension other than
  `.jsonl`. A row that fails validation is reported as unreadable and left alone;
  it is never repaired by guessing a name and never deleted, because a name this
  build cannot have written means something else wrote it.
- Rejecting the whole shape rather than filtering traversal is deliberate. There
  is no sanitizing step that strips `..` and keeps going: a name that needed
  sanitizing is not a name this build generated, and Windows has too many ways to
  spell the same path — trailing dots and spaces, `8.3` short names, alternate
  data streams, reserved device names — for a subtractive filter to be
  trustworthy. The rule is additive: match the generator exactly or be refused.
- Containment is asserted after validation, not instead of it. The path handed to
  the filesystem is always `archive_dir.join(file_name)` with a validated
  single-component `file_name`, and read, delete, and sweep each confirm the
  resolved parent is the archive directory before acting.
- Every entry the code opens, measures, or deletes must be an ordinary file:
  `symlink_metadata` reports a file, and on Windows
  `FILE_ATTRIBUTE_REPARSE_POINT` is clear. A symlink, junction, or other reparse
  point named like an archive is refused by the reader and skipped by the sweep —
  never followed, never measured into the quota, never deleted. Following one
  would let a link planted in the directory serve an arbitrary file to the viewer,
  and measuring one would charge someone else's bytes to the quota. The cost of
  the strict form is that an exotic reparse point that happens to be a real file,
  such as a cloud-storage placeholder, is also refused; in RunCove's own
  subdirectory under `%LOCALAPPDATA%` that case should not arise, and refusing is
  the right way to be wrong.
- A directory named `<uuid>.jsonl` is likewise not an archive. The sweep leaves it
  in place and counts it as an anomaly rather than trying to remove it.
- A row may only name the file its own session generates. Read and delete take a
  `session_id`, and the row's `file_name` is accepted only when it equals
  `<session-id>.jsonl` for that same session — passing the name rule is necessary
  and not sufficient. A row that names a valid archive belonging to a different
  session is refused with a stated reason and neither read nor deleted, and the
  filesystem is not touched. Validity alone would otherwise let one row hand out
  or delete another session's archive, which is the same confusion the name rule
  exists to prevent, one level up.
- A single entry the filesystem refuses is data, not an error. Listing a directory
  returns one classified entry per child or, for a child whose metadata could not
  be read, the fact that it could not be read; only a directory that cannot be
  listed at all stops the sweep. One file another process holds exclusively must
  not prevent every other row from being repaired.


- Exactly one writer thread owns every archive file handle, all byte accounting,
  all eviction, and every write to the index table. Nothing else creates,
  appends to, or deletes an archive file or row. Single ownership is what makes
  quota and index consistency provable instead of hopeful.
- The capture threads (`capture_stream`, `processes.rs:755`) only enqueue. They
  never touch the filesystem, the database, or the quota counter on the
  child-output path.
- Bound the queue by both 4096 records and 8 MiB, whichever is reached first, so
  a runaway child cannot grow memory without limit. On overflow, drop the
  incoming record and count it; never drop an already queued record, which would
  rewrite output that is about to be written.
- The writer emits its own `system` record where output was lost, for example
  `[RunCove: dropped 41 lines / 6218 bytes]`, so the file explains its own gaps
  without the index row.
- Use a buffered writer per session. Flush when the queue drains and at
  finalize. Do not `fsync` per record: a chatty dev server would pay for it on
  every line. A power loss can lose the buffered tail, and a truncated final
  record is discarded on read.
- Take session identity from `ManagedInfo.session_id` (`processes.rs:21`).
  `start_profile_inner_reserved` already calls `begin_session` before `launch`
  (`commands.rs:654`), so read the toggle where the writer handle is created in
  `launch`. "Applies to new sessions only" then follows from construction rather
  than from a runtime check.
- Many sessions are open at once, because restore starts several profiles. The
  writer keys per-session state by session ID and serializes all of them; there
  is no per-session writer thread and no cross-session lock ordering to reason
  about.
- Four locks exist, and the rule differs between them. The open-session state, the
  queue, and the quota total are short in-memory critical sections: a file
  operation or an index call inside one of them is forbidden, because a capture
  thread waits on the first two. The pump's lock is the opposite by design — it
  spans the writer's file and index work, because serializing exactly that is its
  job. So "no lock is held across I/O" is false as a blanket claim and must not be
  written that way; the claim is about the three state locks.
- Where two of them are needed together the order is fixed: open-session state,
  then queue. `enqueue` needs both, because whether a session is still accepting is
  part of the queue's answer.
- `enqueue` is therefore not lock-free and must not be described as never blocking.
  What it guarantees is that a capture thread never waits on a disk or a database:
  it waits only for another in-memory critical section to finish.
- The writer must never hold the storage mutex (`storage.rs:13`) while
  performing file IO, and must never hold the managed-process map mutex at all.

### Durability Semantics

State the guarantee once, because "buffered" and "archived" are not the same
claim.

- One 64 KiB `BufWriter` per open session. `flush` runs when the queue drains,
  when the row counters are refreshed, and at close. A flush hands bytes to the
  operating system; it is not an `fsync`.
- Exactly one `sync_data` per session, at close, in this order: emit a pending
  gap record, flush, `sync_data`, then update the row. A row that says
  `complete` therefore describes bytes that survive a power loss. If `sync_data`
  fails the row becomes `partial` / `write-error` instead of `complete`.
- No per-record `fsync`. A chatty dev server would pay a disk round trip per
  line, and this is a convenience log, not a transaction journal.
- The directory entry is not synced. A power loss can lose a newly created file
  outright; the startup sweep then finds a `writing` row with no file and marks
  it `removed` / `file-missing`.
- What each failure loses:
  - graceful quit: nothing, unless the eight-second drain budget
    (`commands.rs:573`) expires, in which case the remainder is lost and the row
    says `partial` / `interrupted`;
  - RunCove killed from Task Manager or `taskkill`: the queued records and the
    un-flushed buffer tail, at most the queue bounds plus 64 KiB;
  - host power loss or reset: additionally whatever the operating system had not
    written back;
  - disk full or write error: that session closes `partial` / `write-error`,
    other sessions keep writing, and the application keeps running.
- Flushed bytes are visible to a reader immediately through the same page cache,
  which is what lets the viewer tail a session that is still writing.
- Explicit non-goal: this is not a crash-forensics tool. The last line printed
  before a hard reset is not guaranteed to be in the file.

### Drop Accounting

- Queue bounds: 2048 records or 4 MiB per session, 4096 records or 8 MiB across
  all sessions. An enqueue that would exceed any bound is rejected.
- Those four numbers, and the two byte caps in
  [Quota And Eviction](#quota-and-eviction), are passed to the queue and the
  writer as `QueueBounds` and `QuotaLimits` rather than read from a constant at
  the point of use. They are not user settings and no command exposes them; the
  application always passes the documented defaults, which is what
  `the_documented_bounds_are_the_ones_the_defaults_use` pins. The parameter
  exists so an overflow or eviction test can cross a bound with a few short
  records instead of writing 200 MiB, which is the difference between a test that
  runs in milliseconds and one nobody will run.
- The rejected record is always the incoming one. An already queued record is
  never evicted, because dropping it would reorder output that is about to be
  written.
- `dropped_bytes` counts the UTF-8 bytes of the dropped `l` text, not the JSON
  encoding that was never produced. The number means "output lost", not "file
  bytes not written".
- One `system` gap record per contiguous gap, written immediately before the next
  successful record for that session, or at close if no further record arrives:
  `[RunCove: dropped 41 lines / 6218 bytes]`. A gap of exactly one line or one
  byte uses the singular: `[RunCove: dropped 1 line / 1 byte]`. The wording in the
  file is a fixed English string; the file is data, so it stays stable and
  greppable while the badge in the UI is localized.
- Gap records count toward `line_count`, `byte_size`, and the quota, exactly like
  the exit-reason system line.
- **How the queue expresses "per contiguous gap", decided 2026-08-17 with the
  user's approval.** When a record is refused its loss becomes the session's
  pending gap; when the next record for that session is accepted, the queue
  attaches the pending counters to that record and clears them. What the queue
  still owes at the end is therefore only the trailing residual — a loss with no
  accepted record behind it — which the writer writes at close and takes from
  `finish_session`; `take_pending_gap` returns the same residual for a session that
  is still running. Placement in the
  file is then exact, so the bullet above is the contract rather than an
  approximation of it. Two alternatives were weighed and rejected: merging
  everything lost since the last take into one gap, which keeps the counts exact
  but reports a loss before a line that actually preceded it; and putting gap
  markers in the queue itself, which fixes cross-session ordering too but costs
  `drain`'s return type, every test that maps over it, and an exemption from both
  bounds so that a full queue can still record its own loss.
- That decision is implemented as of 2026-08-17, and it needed three things. First,
  somewhere to carry the counters on a queued record. Two candidates were weighed: a
  `gap_before: Option<DropCounters>` field on `ArchiveRecord`, which the capture side
  never sets, or a `QueuedRecord` wrapper that `drain` returns instead, which costs
  every `item.session_id` and `item.line` in the tests one level of nesting. The
  wrapper won, for two reasons beyond the cost. The gap annotates the hand-off, not
  the line the child process wrote, so a field would put it on the wrong type — and
  the capture side then cannot set a gap, because the type it builds has no field for
  one. And `encode_record` writes exactly three keys; a field-borne gap would have
  been silently discarded there, whereas a caller holding a `QueuedRecord` has to
  reach through `record` to encode, which puts `gap_before` in front of whoever wrote
  that line. Second, a `take_pending_gap` that returns the residual only. Third, a
  rewritten assertion at `archive.rs:3369`, where
  `every_short_enqueue_sequence_keeps_the_queues_invariants` required the post-drain
  `take_pending_gap` to hand back everything the session lost across the whole
  sequence; once carried gaps leave with the drained records that is no longer true.
  It now requires that the carried gaps plus the residual equal the session's
  cumulative `dropped`, that the residual is the trailing run and nothing else, and
  that each carried gap sits on the first accepted record after its own drop run —
  positional, so the contract asserted is "this record, and no other, carries this
  run". That was the one assertion changed; it is a contract change with the user's
  approval behind it, not a way to reach green, and the other two gap tests pass
  unchanged.
- **The queue's session accounting ends with the session, added 2026-08-17 after
  review.** The drop history has to survive a drain, so a session's entry cannot be
  removed when its records leave; keeping it forever, however, makes the queue's cost
  grow with the number of sessions the process has ever run rather than with the
  number open, which is not what "bounded queue" can mean.
  `finish_session(session_id) -> AppResult<FinishedSession>` is the one terminal
  operation: it returns `FinishedSession { residual_gap: Option<DropCounters>,
  dropped: DropCounters }` — the gap line to write and the counters the row reports,
  together, because a caller that took one and missed the other would double-report a
  gap or file a row that disagrees with its file — and then removes the entry. It
  refuses while the session has queued records, taking nothing, so the writer's order
  is pump, then finish. A second finish, or one for an unknown session, is
  `FinishedSession::default()`: owed nothing, no losses, so no gap can be written
  twice. The consequence for the writer is that a record enqueued after a finish
  starts a fresh entry with no history and carries no gap, so a session may be
  finished only once its capture threads can no longer enqueue.
- Row counters are cumulative per session, so for a cleanly closed archive the
  sum of its gap records equals `dropped_lines` and `dropped_bytes`. That is a
  test, not a comment.
- Drops do not close a session. Writing continues; `queue-overflow` becomes the
  `partial` reason only if the session also ends without a stronger cause.
- Known bias, not fixed: with a stalled disk and two flooding sessions, a third
  quiet session can lose lines it could not afford. The counters and the gap
  record disclose it. No fairness reservation is added for a case that requires a
  stalled disk.

### Archive Lifecycle

The first draft closed the archive before `finish_session` and therefore before
the exit reason existed. `watch_child` calls `finish_session`
(`processes.rs:575`) and only afterwards builds and publishes the `system` line
that carries the exit reason (`processes.rs:606-613`). Closing first loses that
line; appending after a close writes to a finished archive. Both are wrong. The
order below fixes it without moving `finish_session`.

- Open: insert the index row with status `writing` before the first record is
  written, so a crash or forced termination still leaves a discoverable archive.
- Exit: in `watch_child`, after both capture threads have joined and the exit
  `RunLogEvent` has been built, enqueue that system line and then a close
  request. Leave `finish_session` where it is. The watcher thread does not wait
  for file IO and does not hold the managed map mutex across it; the writer
  flushes, closes the handle, and updates the row.
- The closing boundary is one linearization point, not a pump followed by a state
  change. Under the fixed lock order — open-session state, then queue — the session
  is marked as closing *and* everything it has already accepted is taken out of the
  queue in the same critical section; only then does the file work begin, with both
  locks released. Pumping first and flipping the state afterwards leaves a real
  window, because `enqueue` does not take the pump's lock and can therefore accept a
  record between the last drain and the flip. Every record is then on one side of
  the boundary: accepted before it and written by this close, or refused after it
  and never part of the archive. What is forbidden is a third outcome — a record
  accepted and left in the queue, which would keep the session's entry alive, make
  `finish_session` refuse, and hold queue room the next live session needs.
- The same is required of a close the writer itself starts. A write error or a
  crossed quota closes the session in the middle of a batch, and `enqueue` is still
  accepting until the boundary is established, so records can be both accepted and
  unwritten at that moment. They are removed from the queue and charged to
  `dropped_lines` / `dropped_bytes`, per session, before the row is finalized.
  Discarding a batch remainder without counting it is not acceptable: the row would
  report fewer lost lines than the archive actually lost, and nothing downstream
  could tell a truncated archive from a complete one. A quota close writes no gap
  line for them — the file is stopping at its cap and a gap line is more bytes in
  that same file — so the row's counters are the only surviving record and have to
  be exact.
- Whatever removes a session's queue entry must hand back both halves of its drop
  history at once, and must be able to complete for every session that reaches a
  close. A close that cannot finish its session leaves an entry no later call will
  free.
- An ended session whose archive row still has `ended_at` null is finalizing.
  Render its counters with no reason rather than inventing an error.
- Toggle off: open writers finish the record in hand, then close as `partial`
  with reason `user-disabled`; files are kept. Deleting an archive is always an
  explicit action. Turning the toggle on again affects only sessions started
  afterwards; never backfill a running session and never present a partial file
  as complete.
- Application exit: shutdown drains the queue under a bounded wait consistent
  with the existing eight-second managed-process cleanup budget, then closes
  every still-open session as `partial` with reason `interrupted` if the drain
  did not finish. Report a write failure through the existing lifecycle-error
  channel; never block exit on it.
- Startup sweep, mirroring how unfinished sessions are already repaired
  (`recover_unfinished_sessions`, `storage.rs:725`): for every row still marked
  `writing`, re-measure the file, recount lines, set `ended_at`, and mark
  `partial` with reason `interrupted`; mark a row whose file is gone as `removed`
  with reason `file-missing`; and delete any archive file that has no row. The
  sweep runs before the first write and initializes the quota counter, so the
  counter, the index, and the directory agree before anything is appended.
- The sweep's reach is exactly one directory and exactly one kind of entry. It
  enumerates the immediate children of `<app-data>/run-log-archives/` and never
  recurses, never leaves that directory, and never looks at the data directory
  above it. An entry is eligible only if it is an ordinary file whose name matches
  the generation rule in
  [Archive Directory And Path Constraints](#archive-directory-and-path-constraints).
  Everything else — a subdirectory, a symlink or junction, a name that is not
  `<uuid>.jsonl` — is left untouched and counted as an anomaly the sweep reports
  once. "Delete any archive file that has no row" therefore means "delete an
  eligible file that has no row", and only that.
- Rows are handled by name validation first. A row whose `file_name` fails the
  rule is not measured, not repaired, and not deleted; the sweep marks nothing on
  its behalf and reports it, because a name this build cannot have generated is
  evidence about the database, not a file to clean up.
- Explicit delete: `delete_run_log_archive` refuses with a stated reason while
  that session's writer is open. Windows holds the handle and the delete would
  fail anyway; refusing is truthful and simpler than closing a live archive
  behind the user's back. Eviction skips open sessions for the same reason.

### Archive Initialization Failure

Two different failures, two different answers.

- A failed schema migration is fatal to startup, by existing design:
  `Storage::open` propagates out of the Tauri `setup` closure (`lib.rs:236`) and
  the application does not start. That is the correct outcome — starting without
  persistence would silently lose projects. A failed migration rolls back the
  SQLite transaction and stays at v1; a successful migration has no
  application-level fallback and no database downgrade path. So for the failed
  case the recovery path is "run the previous build", not "repair the database",
  and for the succeeded case the previous build is no longer an option at all: a
  user whose migration succeeded and who then hits an unrelated defect cannot fall
  back to v0.2.1 with that database.
- A failed archive initialization is not fatal. Ports still scan, profiles still
  launch, the live drawer still works, and history still lists sessions, because
  none of that depends on the archive. The failure sources are: the archive
  directory cannot be created, the sweep cannot list or measure it, or the writer
  thread cannot be spawned.
- Degraded state: the feature reports `unavailable` with the reason; no session
  opens a writer; the toggle renders disabled with that reason; badges for
  existing rows still render, because SQLite opened fine; the viewer refuses to
  read and states why; and the failure is surfaced once through the existing
  lifecycle-error channel, never as a modal.
- `unavailable` never degrades to "on". If the toggle was enabled and
  initialization failed, sessions are not archived and the UI says so rather than
  implying capture is happening.
- Retry is user-driven, not a background loop: enabling the toggle retries
  initialization once and reports the outcome, and restarting retries.
- A single unreadable or undeletable file does not abort the sweep. The sweep
  continues over the rest, counts the failures, and for a file it cannot measure
  it uses that row's last known `byte_size` when computing the total. An orphan
  whose delete the filesystem refused stays on disk, so its own length still
  counts.
- An entry whose metadata cannot be read and whose name has no row is the one case
  with no usable number. The total is then unavailable, and unavailable means "no
  room": the archive refuses to grow a directory it cannot measure, because
  under-counting a hard byte cap is how a tool fills someone's disk.
- Unavailable is not a fatal initialization failure and not a new row state. The
  writer initializes, the sweep's repairs still land, and existing badges still
  render; what stops is new output. A session that tries to write closes `partial`
  with reason `quota-exceeded`, which is the truthful in-schema answer — the
  version 2 `CHECK` fixes the reason list, and inventing an `unavailable` reason
  would be a schema change for a state the quota already describes. The
  feature-level `unavailable` the toggle renders comes from the initialization
  report, not from a row.

### Quota And Eviction

- Quota counts bytes durably written to disk. Only the writer produces those
  bytes, so the writer's in-memory total is authoritative; it is initialized by
  the startup sweep from the same measurement that reconciles rows and files.
- Bytes that are queued but not yet written are excluded. The queue bound caps
  that understatement at 8 MiB, and that bound is the documented overshoot.
- What the sweep's measurement counts, stated once because every quota test rests
  on it: an ordinary archive file contributes its own length; a reparse point
  contributes nothing, because it is definitely not the file this build wrote; an
  entry whose metadata could not be read contributes that row's last known
  `byte_size`, because the file may well still be there; the same entry with no row
  contributes nothing measurable and makes the whole total unavailable; and an
  orphan the sweep tried and failed to delete contributes its own length, because
  those bytes are still on the disk. A reparse point and an unreadable entry are
  deliberately different cases: the first is a classification, the second is the
  absence of one.
- Per session: 10 MiB. On reaching it, stop writing that session and close it as
  `partial` with reason `quota-exceeded`.
- In total: 200 MiB. On reaching it, evict whole archives of ended sessions until
  the total is under budget. A session is eligible only when its `status` is
  `complete` or `partial` *and* its `ended_at` is non-null, and never when this
  writer still holds it open. Both halves are checked in the writer, not left to
  the schema: `CHECK ((status = 'writing') = (ended_at IS NULL))` makes an ended
  row with no `ended_at` impossible in a database this build wrote, but a row from
  elsewhere has to be skipped rather than sorted, because a session with no end has
  no place in an order keyed on when sessions ended and a missing timestamp read as
  zero would make it the first candidate of all.
- Eviction order is `ended_at`, then `started_at`, then `session_id`, oldest first.
  `ended_at` is the key because the question is which archive has been finished
  longest; `started_at` breaks a tie between archives that ended together, and the
  session id makes the choice deterministic when both timestamps agree. If the
  total is still over budget after every eligible archive is gone, stop writing all
  open sessions and close them as `partial` with reason `quota-exceeded`.
- Eviction order on disk is file first, then row. A crash between the two leaves
  a row whose file is missing, which the startup sweep marks `removed` with
  reason `file-missing`. A crash before the delete leaves both, and the next
  eviction retries. No ordering leaves an undiscoverable orphan file.
- A file the writer really deleted has really freed its bytes, so the in-memory
  total is credited with the length measured on disk even when the row update that
  follows fails. Crediting the row's `byte_size` instead would refuse room the
  directory actually has, and the two figures can disagree by any amount. The
  inconsistent row is left for the next startup sweep to repair, and the failure is
  reported rather than swallowed. Both paths obey this: quota eviction and
  `delete_run_log_archive`.
- Every quota decision, reservation, eviction choice, file delete, and row update
  happens on the writer thread in one sequence. There is no path where two
  sessions can each believe they hold the last free byte.

### Index Model

The first draft used one nullable `incomplete_reason` column for both "this
archive is partial" and "this archive was evicted", which cannot express a
complete archive that was later reclaimed. Split them.

- `status` is one of `writing`, `complete`, `partial`, `removed`.
- `reason` is null unless `status` is `partial` or `removed`, and non-null when it
  is. The `CHECK` has to say `reason IS NOT NULL` out loud to enforce the second
  half; see the three-valued-logic note in
  [Migration v1 To v2](#migration-v1-to-v2).
  - `partial`: `write-error`, `quota-exceeded`, `queue-overflow`,
    `interrupted`, `user-disabled`.
  - `removed`: `quota-evicted`, `user-deleted`, `file-missing`.
- When more than one partial cause occurs, keep the most severe by that fixed
  order: `write-error`, then `quota-exceeded`, then `queue-overflow`, then
  `interrupted`, then `user-disabled`.
- Always show `dropped_lines` and `dropped_bytes` next to the reason so a
  partial archive is never mistaken for complete output.
- Do not claim redaction. Child `stdout` and `stderr` are arbitrary text and can
  contain keys, tokens, and business data, and no reliable automatic filter
  exists for them. The toggle, the Help topic, and `README.md:162-163` must state
  that an enabled archive may contain secrets and that the feature is off by
  default.

### Read Path And Cursor

The cursor is a byte offset, not a line number. The file is append-only, so bytes
below the current length never change: an offset returned once stays a valid
record boundary forever, and paging backwards never shifts because new output can
only appear beyond the length the reader measured.

- `read_run_log_archive(session_id, before_offset, max_lines)`.
  - `before_offset` absent means "the end of the file": return the last records.
    That is the default, because the reason to open a run log is what it printed
    last.
  - `before_offset` present must be a boundary this command returned earlier:
    `0 < n <= file_length` and the byte at `n - 1` must be `\n`. Anything else is
    rejected with an explicit invalid-cursor error rather than silently resyncing
    to a nearby newline, so a client bug is visible instead of returning
    plausible garbage.
  - Records returned are those wholly contained in `[0, before_offset)`, in file
    order, oldest first within the page.
- `max_lines` is clamped to 1..=2000 and defaults to 500. A page also stops at
  1 MiB of accumulated text, because 64 lines at the 16 KiB per-line bound would
  otherwise be an 8 MiB IPC payload. The response says which bound stopped it:
  `lines`, `bytes`, or `start`.
- The response carries `page_start_offset` — feed it back as the next
  `before_offset` — plus `has_more_before`, the measured `file_length`, and the
  index row's `status`, `reason`, `line_count`, `byte_size`, `dropped_lines`, and
  `dropped_bytes`. The reader never counts the whole file to answer
  `line_count`; the writer maintains it.
- Row counters are refreshed by the writer at most once per four seconds or per
  1 MiB written, and always at close. A writing session's badge is therefore
  stale by at most that much, while the viewer's `file_length` is exact because
  it is measured at read time. Tail again to see newer output.
- The backward scan reads fixed 64 KiB blocks from the end until it has one more
  record boundary than it needs, or reaches offset 0. It never loads the whole
  file, and the 10 MiB per-session cap bounds the worst case anyway.
- Bytes after the final `\n` are not a record and are skipped, with
  `incomplete_tail_skipped` set. For a `writing` archive that is a record
  mid-flush and may complete later; for a closed archive it is a torn write from a
  crash. Same flag, different wording in the UI, decided by `status`.
- A record that is not valid JSON of the expected shape is skipped and counted in
  `malformed_lines`. One bad record never fails the page.
- Reading a `removed` archive fails with that row's reason, so a viewer left open
  across an eviction says "reclaimed by quota" instead of showing an empty file.
- The command reads the index row under a short storage lock, releases it, and
  only then opens the file. It runs through `run_blocking` (`commands.rs:553`),
  so a multi-megabyte read never blocks the IPC thread.

## Interfaces And Data

### Migration v1 To v2

Implemented on 2026-08-15. `migrate` now gates on `SCHEMA_VERSION`
(`storage.rs:621`) and rejects anything above it (`storage.rs:625`); the v1
creation batch still stamps `PRAGMA user_version=1` (`storage.rs:668`) and
`upgrade_to_version_2` (`storage.rs:689`) adds one table and stamps 2. No existing
table is altered, no column is dropped, and no row is rewritten, so a v1 database
upgrades in place and a v2 database opens unchanged. A fresh install runs
0 → 1 → 2 as two separate atomic transactions, either of which is resumable on the
next launch; the v1 → v2 upgrade itself is one transaction.

```sql
CREATE TABLE run_log_archives (
  session_id    TEXT PRIMARY KEY REFERENCES run_sessions(id) ON DELETE CASCADE,
  file_name     TEXT NOT NULL,
  status        TEXT NOT NULL
                CHECK(status IN ('writing','complete','partial','removed')),
  reason        TEXT,
  line_count    INTEGER NOT NULL DEFAULT 0 CHECK(line_count >= 0),
  byte_size     INTEGER NOT NULL DEFAULT 0 CHECK(byte_size >= 0),
  dropped_lines INTEGER NOT NULL DEFAULT 0 CHECK(dropped_lines >= 0),
  dropped_bytes INTEGER NOT NULL DEFAULT 0 CHECK(dropped_bytes >= 0),
  started_at    INTEGER NOT NULL,
  ended_at      INTEGER,
  CHECK ((status IN ('writing','complete') AND reason IS NULL)
      OR (status = 'partial' AND reason IS NOT NULL AND reason IN
           ('write-error','quota-exceeded','queue-overflow','interrupted',
            'user-disabled'))
      OR (status = 'removed' AND reason IS NOT NULL AND reason IN
           ('quota-evicted','user-deleted','file-missing'))),
  CHECK ((status = 'writing') = (ended_at IS NULL)),
  -- Every archived byte belongs to some line, so bytes cannot be lost
  -- without losing a line. The converse is false and must stay legal:
  -- a captured line may be empty, so dropping one costs 1 line and
  -- 0 bytes.
  CHECK (dropped_bytes = 0 OR dropped_lines > 0)
);
CREATE INDEX idx_run_log_archives_status_ended
  ON run_log_archives (status, ended_at);
```

- **The drop-counter constraint was corrected on 2026-08-17, with the user's
  approval.** It used to read `CHECK ((dropped_lines = 0) = (dropped_bytes = 0))`,
  which claimed lines and bytes are lost together. They are not: `capture_stream`
  emits a real event with an empty `line` for a lone newline, so dropping one costs
  `dropped_lines = 1, dropped_bytes = 0`, and the old constraint refused it. Only the
  reverse — bytes without a line — is impossible, which is what the one-directional
  form above says. The correction landed in all four places at once: this DDL, the
  production migration (`storage.rs:715`), the pinned `V2_ADDITION`
  (`storage.rs:1240`), and the `"drop counters agree"` rejection case in
  `the_archive_index_rejects_impossible_rows`, which was removed because the row it
  refused is ordinary data — a comment at `storage.rs:1553` says so in place, and the
  two directions are pinned instead by `an_archive_row_may_lose_a_line_that_carried_no_bytes`
  (`storage.rs:1602`) and `an_archive_row_may_not_lose_bytes_without_losing_a_line`
  (`storage.rs:1648`), each of which holds the migrated and the pinned schema to the
  same rule. The schema version stays at 2 on both sides — the production
  `SCHEMA_VERSION` (`storage.rs:621`) and the deliberately separate test literal
  `CURRENT_SCHEMA_VERSION` (`storage.rs:773`) — and no version 3 step
  was added: the version 2 code is unreleased and uncommitted, and the two verified
  developer databases on this machine were confirmed at `user_version = 1` on
  2026-08-16 and again on 2026-08-17, so neither they nor the published baseline is an
  incompatible artifact to signal against. That is the claim's whole scope — an
  unmeasured machine is not covered. Should a version 2 database ever be found,
  editing this DDL cannot repair it — SQLite keeps a `CHECK` inside the table
  definition — and the repair is the table rebuild recorded in `HANDOFF.md`.
- The status and reason rules are database constraints, not comments, in the same
  style as the v1 `protocol` and `source` checks (`storage.rs:645-653`). A bug
  cannot persist an impossible pair. The cost is that adding a reason later needs
  a table rebuild in a future migration, which for a table this small is cheap.
- Each `reason` arm needs its own explicit `reason IS NOT NULL`, and the reason is
  SQL three-valued logic. The first two drafts of this DDL wrote
  `status = 'partial' AND reason IN (...)`, which does not reject a null reason:
  `NULL IN (...)` evaluates to NULL, `1 AND NULL` to NULL, the surrounding
  `0 OR NULL OR 0` to NULL, and a SQLite `CHECK` **passes** when its expression is
  NULL rather than failing. The constraint therefore admitted exactly the rows it
  was written to forbid — a `partial` or `removed` archive carrying no reason,
  which the user interface would render as a badge with no explanation. Found on
  2026-08-15 by `the_archive_index_rejects_impossible_rows`, which reported
  `partial must carry a reason: ('sess-exited','a.jsonl','partial',NULL,...) was
  accepted` after the migration first landed. Fixed in the migration, in the
  test's pinned `V2_ADDITION`, and in the DDL above, and pinned by a ninth
  rejection case covering the `removed` arm. Reading the expression alone does not
  reveal this; only the executed test does.
- No `IF NOT EXISTS`. A pre-existing `run_log_archives` object means something is
  wrong, and a loud failure that rolls back is better than adopting a table whose
  shape is unknown.
- The whole step is one transaction with `PRAGMA user_version=2` as its last
  statement, the same shape used to create version 1 (`storage.rs:630-670`).
- One sentence describes the migration, and every document, release note, and
  commit message uses it unchanged:

  > 迁移失败时 SQLite 事务回滚并保持 v1；迁移成功后没有应用级回退或数据库降级路径。

  In English, the wording these documents carry: **a failed migration rolls back
  the SQLite transaction and stays at v1; a successful migration has no
  application-level fallback and no database downgrade path.** The two halves are
  not a pair, and neither half is a rollback of the other. Do not write
  "revertible", "rollback", or "downgrade" about a migration that succeeded.
  - What "stays at v1" buys, concretely: the transaction rolls the header back with
    the tables, so the database is opened unchanged by this build and by v0.2.1 and
    user data is untouched. Asserted by
    `a_failed_migration_leaves_the_version_1_database_intact`.
  - What "no application-level fallback" costs, concretely: once the migration
    commits, the database is at version 2 and **v0.2.1 can no longer open it** —
    that build rejects any `user_version` above 1. No code returns a version 2
    database to version 1, so a user who then hits an unrelated defect cannot go
    back to v0.2.1 with that database.
- Store `file_name` relative to the archive directory, never an absolute path.
  The application-local data directory differs per user and per machine, and a
  stored absolute path would be wrong the moment either changes. The column is a
  single validated path component, not a path: every read of it is checked against
  the generation rule before it is joined to anything. See
  [Archive Directory And Path Constraints](#archive-directory-and-path-constraints).
  A `NOT NULL TEXT` column cannot express that rule, so the check lives in code
  and is pinned by tests rather than by a `CHECK`.
- The row survives eviction: an evicted archive becomes `removed` /
  `quota-evicted` rather than a deleted row, so history can distinguish "never
  archived" from "archived and later reclaimed". Nothing in the code deletes
  `run_sessions` rows today (`storage.rs:312-335` are the only writes), so the
  cascade is defensive, not a routine path.
- The index exists for eviction, which selects ended archives oldest first.

  `reason` is null exactly when `status` is `writing` or `complete`; each status
  admits only its own reasons; `ended_at` is null exactly when `status` is
  `writing`; counters only ever increase within a session; and `dropped_bytes > 0`
  implies `dropped_lines > 0`, with no converse — a dropped empty line is
  `1 line / 0 bytes` and is ordinary data.
- `mock-data.ts` must produce all five badge shapes — absent, `complete`,
  `partial` with a reason and drops, `removed`, and a `writing` session — so the
  unit tests and the Playwright flow exercise every state without a backend.

## Documentation Authority

`README.md` nor Help is authoritative. One rule replaces both:

- Code plus passing tests define actual behavior. A document never overrides
  them.
- `README.md` is authoritative for install steps, architecture, privacy claims,
  and release scope.
- In-app Help is authoritative for operating steps.
- Where the two overlap, `README.md` wins and Help is corrected to match.
- A document that disagrees with verified behavior is a defect. Fix the document
  and add the test that would have caught it, in the same change.

## Deferred: Project Git Status

Not approved, not scheduled, not implemented. It was the second milestone of the
first draft and is removed from v0.3.0. Before it is worth a version of its own,
these have to be answered.

- Justification first. It closes no limitation this repository documents, and it
  duplicates what the editor and Git client already open next to RunCove. The
  burden is to name a task RunCove would do better, not to list what a status
  line could display. If that cannot be named, drop the feature.
- The "hard timeout" in the first draft is not implementable. A synchronous
  library call cannot be aborted from outside; the honest forms are a bounded,
  cancellable walk (`gix` with `should_interrupt`), a separate helper process
  that can actually be killed, or a soft deadline with the residual risk
  admitted. Under a soft deadline a stuck worker keeps its concurrency slot
  until it returns, and the plan must say so.
- Minimum toolchain. Verify the chosen crate builds on the declared minimum
  before locking a version. Note that nothing enforces the declarations today:
  the desktop crate says `rust-version = "1.77"`
  (`apps/desktop/src-tauri/Cargo.toml:7`), the root says `1.74`, and every CI
  and release job installs `dtolnay/rust-toolchain@stable`. A dependency with a
  higher floor would silently falsify both instead of failing a check. Either add
  a job that builds on the declared minimum or remove the declarations.
- Dependency cost. `gix` or `git2` is a large new tree, and therefore a new audit
  surface and build-time cost, in a repository that has no `cargo-deny` or
  `cargo audit` job.
- Object scope, still undefined: the repository root against a profile's `cwd`
  subtree; nested repositories and monorepos; whether untracked files, ignored
  files, and dirty submodules count as dirty; and the exact wording for no
  upstream, detached `HEAD`, and diverged branches.
